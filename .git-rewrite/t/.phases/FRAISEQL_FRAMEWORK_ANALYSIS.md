# FraiseQL Framework Analysis for Performance Assessment

## Executive Summary

FraiseQL is a high-performance GraphQL framework that combines Python's developer experience with Rust's execution engine. For this performance assessment, **the rich WhereType system auto-generates complex queries**, eliminating the need for manual resolver implementations that other frameworks require.

**Key implication**: All Phase 7 workloads (aggregations, pagination, search, mutations) work automatically—frameworks don't need to implement them. Phase 8 measures how efficiently FraiseQL executes these auto-generated queries.

## WhereType System (Auto-Generated Queries)

### What is WhereType?

WhereType is FraiseQL's type-safe query builder that generates GraphQL input types from database schema. It eliminates manual resolver implementation for:

1. **Filtering** - WHERE clause generation
2. **Aggregation** - COUNT, SUM, GROUP BY
3. **Pagination** - limit/offset, cursor-based
4. **Sorting** - ORDER BY with multiple fields
5. **Search** - Full-text search operators

### How WhereType Works

```python
# Define entity type from database
@fraiseql.type(sql_source="tb_user")
class User:
    id: UUID
    username: str
    email: str
    bio: str | None = None

# WhereType automatically creates:
# - UserWhereInput (all filtering operators)
# - UserOrderByInput (sort fields)
# - Aggregation resolvers (count, sum, avg, etc.)
# - Cursor-based pagination helpers
```

### Auto-Generated GraphQL Input Type Example

```graphql
# Auto-generated by WhereType for User type:
input UserWhereInput {
  # Equality operators
  id: IDWhereInput
  username: StringWhereInput
  email: StringWhereInput
  bio: StringWhereInput

  # Logical operators
  AND: [UserWhereInput!]
  OR: [UserWhereInput!]
  NOT: UserWhereInput
}

# StringWhereInput expands to:
input StringWhereInput {
  equals: String
  not: String
  in: [String!]
  notIn: [String!]
  contains: String           # ILIKE
  startsWith: String         # ILIKE prefix
  endsWith: String           # ILIKE suffix
  search: String             # Full-text search (tsvector)
  mode: QueryMode            # INSENSITIVE
}

# Aggregation auto-generated:
type UserStats {
  count: Int!
  avgAge: Float
  maxAge: Int
  minAge: Int
}
```

## Phase 7 Workload Compatibility

### How Each Phase 7 Workload Uses WhereType

**1. Simple Queries** ✅
```graphql
query {
  ping  # Direct resolver, minimal overhead
}
```
- No WhereType involved
- Throughput test (protocol overhead)
- Expected: 1000+ req/sec

**2. Parameterized Queries** ✅
```graphql
query {
  users(where: {username: {equals: "user_1"}}, limit: 10) {
    id username email
  }
}
```
- WhereType generates: `UserWhereInput` with `StringWhereInput`
- Translates to: `WHERE username = 'user_1'`
- Expected: p99 < 100ms

**3. Aggregation Queries** ✅
```graphql
query {
  userStats: users(where: {id: {gt: 1000}}) {
    stats {
      count
      avgAge: avg(age)
    }
  }
}
```
- WhereType auto-generates: `UserStatsInput` with aggregators
- Translates to: `SELECT COUNT(*), AVG(age) ... WHERE id > 1000`
- Expected: p99 < 200ms

**4. Pagination (Offset)** ✅
```graphql
query {
  users(where: {status: {equals: "active"}}, limit: 20, offset: 100) {
    id username
  }
}
```
- WhereType: `where` parameter
- Offset-based: `LIMIT 20 OFFSET 100`
- Expected: Degrades at large offsets (100+ pages)

**5. Pagination (Cursor)** ✅
```graphql
query {
  usersConnection(first: 20, after: "cursor_xyz") {
    edges { node { id } cursor }
    pageInfo { hasNextPage endCursor }
  }
}
```
- WhereType: Cursor encoding auto-generated
- Cursor-based: `WHERE (created_at, id) > (timestamp, id)`
- Expected: Consistent performance at any offset

**6. Full-Text Search** ✅
```graphql
query {
  searchUsers(query: "database OR performance") {
    id username bio
  }
}
```
- WhereType: `search` operator in `StringWhereInput`
- Uses: PostgreSQL tsvector `@@` operator
- Requires: GIN index on search_vector column
- Expected: p99 < 150ms

**7. Deep Traversal** ✅
```graphql
query {
  users(limit: 3) {
    posts(limit: 2) {
      comments(limit: 2) {
        author { username }
      }
    }
  }
}
```
- WhereType: Nested types for related entities
- N+1 prevention: Via TV tables (materialized views)
- Expected: <1 query per field if batched properly

**8. Mutations** ✅
```graphql
mutation {
  createPost(input: {title: "...", content: "..."}) {
    id title author { username }
  }
}
mutation {
  updateUser(id: 1, input: {bio: "..."}) {
    id username bio
  }
}
```
- Not WhereType-driven (explicit mutations)
- Transaction handling: Built-in
- Expected: p99 < 200ms

## Performance Characteristics

### What FraiseQL Optimizes For

| Aspect | Benefit | Measurement |
|--------|---------|-------------|
| **Query Generation** | Rust pipeline speeds up WHERE clause compilation | Query planning latency |
| **Async I/O** | asyncpg pool handles concurrent requests | Connection utilization |
| **Type Safety** | Compile-time validation prevents SQL errors | Error rate (should be 0%) |
| **Caching** | Query plans cached, WHERE clauses compiled once | Cache hit ratio |
| **Batch Loading** | TV tables reduce N+1 via materialized views | Query count per request |

### Performance Expectations by Workload

| Workload | CPU Usage | Memory | Connections | Queries per Request |
|----------|-----------|--------|-------------|-------------------|
| Simple (ping) | 1-5% | 50MB | 1-2 | 1 (cached) |
| Parameterized | 10-20% | 100MB | 5-10 | 1-2 (index lookup) |
| Aggregation | 20-30% | 150MB | 10-15 | 1 (GROUP BY in DB) |
| Pagination (offset) | 15-25% | 100MB | 8-12 | 1-2 |
| Pagination (cursor) | 15-25% | 100MB | 8-12 | 1-2 |
| Full-text | 25-35% | 200MB | 12-18 | 1 (GIN index) |
| Deep Traversal | 30-40% | 250MB | 15-20 | 3-5 (TV tables) |
| Mutations | 20-30% | 150MB | 10-15 | 2-4 (with transaction) |

## What Phase 8 Will Measure for FraiseQL

Since WhereType handles all query generation, Phase 8 focuses on **execution efficiency**:

### 1. Query Generation Overhead
- Time to compile WHERE clauses in Rust pipeline
- Expected: <1ms per query
- Measurement: Internal request timing (if available)

### 2. Connection Pool Efficiency
- Active/idle connection ratios during different workloads
- Overflow connection usage under peak load
- Expected: <10% overflow usage during sustained load

### 3. Memory Pressure
- Pydantic model validation memory cost
- Query result buffering
- Expected: Linear growth with concurrent load

### 4. N+1 Detection via TV Tables
- Query count per request
- Batching effectiveness
- Expected: <1 additional query per relationship

### 5. Database Index Utilization
- Query plan analysis during aggregation/search
- GIN index effectiveness for full-text search
- Expected: All queries use indexes (0 seq scans)
