## Gap Analysis & Closure Plan

### Gap 1: Async Database Pooling (CRITICAL - Phase 3)

**Problem**: All frameworks use synchronous psycopg2 with single connections
- FraiseQL async potential blocked by sync DB
- FastAPI (async) forced into sync context
- Single connection = sequential execution = 10-100x throughput loss

**Solution Architecture**:
```
All Python frameworks (5):
├── Async wrapper: frameworks/common/async_db.py
│   ├── asyncpg.create_pool(min=10, max=50)
│   ├── Statement caching (100 prepared)
│   └── Pooling metrics collection
│
├── FraiseQL
│   ├── Switch from psycopg to asyncpg
│   ├── Activate TV table reads (already configured)
│   └── Pool: min=20, max=100 (has TV tables)
│
├── Strawberry + Graphene
│   ├── Async resolvers with asyncpg
│   ├── DataLoader for N+1 prevention
│   └── Pool: min=10, max=50
│
├── FastAPI REST
│   ├── Async/await throughout
│   ├── Connection pool per request scope
│   └── Pool: min=10, max=50
│
└── Flask REST
    ├── Keep psycopg3 pool (sync framework)
    ├── Use psycopg.AsyncConnection for warm requests
    └── Pool: min=5, max=30 (less concurrency)
```

**Implementation Steps** (Sequential - 2-3 days):
1. **Create async database module** (`frameworks/common/async_db.py`)
   - asyncpg pool creation, statement caching
   - Wrapper methods: fetch(), fetchrow(), execute()
   - Metrics collection (connections active, wait time)

2. **Refactor FraiseQL** (`frameworks/fraiseql/main.py`)
   - Switch to asyncpg pool (already in requirements)
   - Verify TV table reads working
   - Update resolvers to use async_db module
   - Set pool: min=20, max=100 (CQRS=more connections)

3. **Refactor Strawberry** (`frameworks/strawberry/main.py`)
   - Switch from psycopg2 to asyncpg
   - Add DataLoader for N+1 prevention
   - Convert resolvers to async/await
   - Set pool: min=10, max=50

4. **Refactor Graphene** (`frameworks/graphene/main.py`)
   - Same as Strawberry (same issue)
   - Add DataLoader integration
   - Convert to async

5. **Refactor FastAPI REST** (`frameworks/fastapi-rest/main.py`)
   - Use asyncpg instead of psycopg2
   - Proper async/await patterns
   - Pool per request lifecycle

6. **Enhance Flask REST** (`frameworks/flask-rest/main.py`)
   - Upgrade to psycopg3 with pool support
   - Keep synchronous (Flask constraint)
   - Pool: min=5, max=30

7. **Update all requirements.txt**
   - Replace psycopg2 with asyncpg
   - Add dataloader if applicable
   - Update docker-compose volumes

8. **Verification**:
   - Run: `python run_comparative_benchmarks.py --framework fraiseql`
   - Expected: 2-5x throughput improvement
   - Check pool utilization in logs
   - Verify TV tables being used

**Files to Create/Modify**:
| File | Action | Purpose |
|------|--------|---------|
| `frameworks/common/async_db.py` | Create | Shared async pool |
| `frameworks/fraiseql/main.py` | Refactor | Enable asyncpg + TV tables |
| `frameworks/strawberry/main.py` | Refactor | asyncpg + DataLoader |
| `frameworks/graphene/main.py` | Refactor | asyncpg + DataLoader |
| `frameworks/fastapi-rest/main.py` | Refactor | Full async + asyncpg |

### Gap 2: Data Volume Scaling (Phase 4)

**Problem**: ~500 records fit in RAM, can't test index/memory pressure

**Solution Architecture**:
```
Current: 100 users, 500 posts, 2000 comments
Target:  10K users, 100K posts, 500K comments

Timeline:
├── 1min: Generate users (10K with Faker)
├── 2min: Generate posts (100K with relationships)
├── 3min: Generate comments (500K with threading)
├── 1min: Create indexes
├── 1min: Sync FraiseQL TV tables
└── Total: ~8 minutes for full dataset
```

**Implementation Steps** (Sequential - 1-2 days):

1. **Create data generator** (`database/seed-generator.py`)
   - Faker-based reproducible generation
   - Configurable sizes: --users 10000 --posts 100000 --comments 500000
   - Batch inserts for performance
   - Seed=42 for reproducibility

2. **Create SQL batching** (`database/04-large-dataset.sql`)
   - Alternative: stored procedures with batch loops
   - Or: COPY format for SQL-only approach

3. **Add Makefile targets**:
   ```makefile
   seed-small: # 100 users, 500 posts, 2K comments (dev)
   seed-medium: # 1K users, 10K posts, 50K comments (testing)
   seed-large: # 10K users, 100K posts, 500K comments (production)
   ```

4. **Update docker-compose.yml**:
   - PostgreSQL: shared_buffers=256MB → 512MB
   - PostgreSQL: effective_cache_size=1GB → 2GB
   - Volume size: 10GB

5. **Generate JMeter datasets** (`tests/perf/jmeter/datasets/`)
   - CSV with realistic user IDs
   - CSV with post IDs for parameterization
   - Both for concurrent scenario testing

6. **Verification**:
   - Run: `make seed-large && psql -c "SELECT COUNT(*) FROM benchmark.tb_user;"`
   - Expected: users=10000, posts=100000, comments=500000
   - Check disk usage: should be ~1-2GB
   - Check indexes: `ANALYZE` to update stats

**Files to Create/Modify**:
| File | Action | Purpose |
|------|--------|---------|
| `database/seed-generator.py` | Create | Configurable data generation |
| `database/04-large-dataset.sql` | Create | SQL-based generation (alternative) |
| `database/03-data.sql` | Replace | Keep for dev, use seed-small |
| `Makefile` | Create | seed-small, seed-medium, seed-large targets |
| `docker-compose.yml` | Update | PostgreSQL memory configs |
| `tests/perf/jmeter/datasets/*.csv` | Create | Parameterized test data |
